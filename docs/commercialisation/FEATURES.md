# NIGHTINDEX commercial feature register

**Planning baseline: 24 November 2026.** Every row is a proposed requirement or an extension of an existing foundation. A target phase is an implementation sequence, not a claim that the capability exists or a delivery promise. The [source baseline](BASELINE_AND_SOURCES.md) records current capabilities separately.

Read the [dossier](../../COMMERCIALISATION.md), [product specification](PRODUCT_SPEC.md), [roadmap](../../ROADMAP.md) and [validation plan](VALIDATION.md) for rationale and detailed behaviour.

## Priority and phase definitions

- **P0:** required for trustworthy historical accounting or the first bounded paid workflow.
- **P1:** required for the supported commercial desktop release, or its selected customer segment.
- **P2:** an extension to fund only when demand and feasibility justify it.

Phases are **M0** baseline and discovery; **M1** historical catalogue; **M2** verified reconciliation and operator pilots; **M3** usable desktop beta; **M4** commercial release; **M5** imaging and selected metadata/recovery adapters; **M6** validated team/remote extensions. Early design spikes can run ahead of a phase, but a feature cannot bypass its evidence prerequisites.

## Historical knowledge and media

| ID | Capability and scope | Priority / first target | Observable acceptance condition |
| --- | --- | --- | --- |
| F01 | Case catalogue: collect media, manifests, images, scans, policies and decisions under a durable case ID. Separate physical assets, logical sources, file occurrences and content identities. | P0 / M1 | Two cases with the same display labels remain distinct; a complete case can be reopened without the original disks. |
| F02 | Immutable observations and scan coverage: completed/partial/failed/cancelled runs, exclusions, errors, observed scope, snapshot/consistency context, historical generations and source changes. | P0 / M1 | Interrupted or permission-denied scans preserve history and expose gaps. A completed live walk reports items not observed, without claiming snapshot consistency or declaring them deleted or permanently lost. |
| F03 | Historical existence and loss account: first/last observed version, last path/media, verified alternatives, candidate copies, unresolved sources, closure/reopening and a useful next action. | P0 / M1 | Search finds a previously observed file after its source disappears. A later exact verified copy resolves the lead with provenance; a similarly named different version does not. |
| F04 | Typed identity and verification evidence: full cryptographic digests, algorithms, stream lengths, extents, timestamps, imported/fresh/cached provenance and source stability. | P0 / M1 | A cache hit retains the original byte-read time. Same size/mtime with changed content cannot be labelled freshly verified. Partial/similarity hashes cannot establish complete identity. |
| F05 | Offline collection search: paths, names, types, timestamps, tags, hashes, media, version relationships and historical views across disconnected sources. | P0 / M1 | A query returns the last recorded location and verification age without mounting media, and explains absence of catalogue evidence without claiming never-existence. |
| F06 | Media passports: stable internal IDs, corroborating serial/WWN/UUID observations, human label, shelf/bay, QR/barcode, online/offline state, clone/adapter ambiguity and check-in history. | P0 / M1; labels in M3 | Reusing a mountpoint or seeing duplicated filesystem IDs cannot silently bind an old job to a different device. A printed label opens the correct media record. |
| F07 | Topology and membership: physical disk to partition, pool/vdev/array, volume, dataset, snapshot and image relationships; missing/extra members and confidence in inferred layouts. | P1 / M2 basic; M5 specialised | A case identifies known members and gaps without implying the pool is recoverable. Unsupported layouts remain explicit; inferred topology is separate from observed labels. |
| F08 | Read budgets and health observations: explicit inventory/verify/enrich/fragile-source modes, bounded retries, prioritisation, health snapshots and acquisition-first workflow. | P0 / M2; device adapters M5 | Inventory mode avoids content enrichment; fragile mode respects budgets and does not silently run self-tests, repair or scrub. Health observations carry time and source, not a guarantee. |
| F09 | Imports: existing NIGHTINDEX databases, CSV/JSON manifests, backup inventories, directory listings and selected recovery/catalogue exports with preserved original artifacts and parser versions. | P0 / M1 legacy and generic; P1 / M3 selected | Re-import is idempotent; an old mutable database becomes evidence with unknown completeness, not invented historic snapshots. Conflicts and malformed records are reported, not silently dropped. |

## Reconciliation and operator work

| ID | Capability and scope | Priority / first target | Observable acceptance condition |
| --- | --- | --- | --- |
| F10 | Multi-source reconciliation: exact duplicates, renamed trees, divergent versions, partial overlaps, related archives and explainable candidate ranking. | P0 / M2 | Exact-byte groups and heuristic candidates remain separate. Every accepted match exposes its evidence; a high folder score cannot certify all constituent bytes. |
| F11 | Verified copy and consolidation: immutable plan, precondition checks, copy staging, explicit no-clobber behaviour, verification, durability policy and per-item results. | P0 / M2 | The selected copy path detects changed sources, corrupted destinations and late destination conflicts. `Copied`, `verified` and metadata-preservation outcomes remain separate. |
| F12 | Durable jobs: pause/cancel, checkpoints, retries/backoff, resumable plans, source revalidation, structured logs and progress independent of the GUI. | P0 / M2 | Restarting after interruption continues only valid work, preserves failure evidence and does not repeat a destructive action. All execution paths share the same result semantics. |
| F13 | Preservation contract: tested contents, timestamps/precision, permissions/ownership, ACLs/xattrs, links, sparse files, raw names, ADS/resource forks as supported by each platform. | P0 / M2 selected; P1 / M4 matrix | Unsupported requested preservation is rejected or explicitly accepted as an exception. Case/name collisions and metadata loss appear before execution. |
| F14 | Desktop GUI: case overview, media shelf, offline search/history, comparison review, loss account, plans, jobs, reports and catalogue care; accessible, keyboard-friendly, virtualized large views. | P1 / M1 prototype; M3 beta | An operator other than the author completes intake, finds an old file, explains its evidence and exports a report without shell commands or author intervention. Long jobs do not freeze the UI. |
| F15 | Optional content enrichment: safe previews/thumbnails, bounded text extraction, project/dependency context and later local semantic search. | P2 / M3 limited preview; later demand | Enrichment is opt-in and isolated, respects content/read budgets and does not upload data. Candidate search results never become identity evidence solely through an embedding or language-model judgement. |
| F16 | Real archive catalogue: parser-backed entries, nesting, encrypted/truncated states, virtual paths, format limits, optional member hashing and source-member provenance. | P1 / M3 selected formats | A fixture's real member list is reproduced with coverage and limits. Truncation, passwords and expansion limits are explicit. Filename-derived archive relations remain labelled as such. |
| F17 | Acquisition integration: GNU ddrescue image/map import, optional supervised orchestration, progress/resume and retained acquisition provenance. | P2 / M5 | An interrupted image retains its map; unread ranges remain unknown even if the image has full apparent length. No output is mistaken for a fully acquired original. |
| F18 | Metadata-only salvage: selected filesystem/recovery adapters to recover names, parent/object relationships and other surviving metadata without assuming content exists. | P2 / M5 | Each recovered entry links to its image/source, tool version and evidence; missing metadata is reported as unknown. Supported damaged fixtures have ground-truth comparisons. |
| F19 | Selected block/array reconstruction: narrowly supported RAID/ZFS layouts and selected file extraction, only after topology and metadata work. | P2 / M5 research, separately funded | A named layout/version/failure class passes its corpus before support is advertised. Missing members never trigger a blanket promise of filenames, recoverable bytes or completeness. |
| F20 | Integrity rechecks and alerts: scheduled verification on healthy sources, verification-age review, newly missing observations and newly found candidates/copies. | P1 / M3 manual; M4 scheduling | A recheck distinguishes stale cached evidence from fresh reads. Alerts explain scope and cause; no routine full-read schedule is imposed on failing media. |

A schema/policy change is explicit; plugins have a declared capability boundary and cannot silently escalate scope. |

| Discussed need | Requirements and delivery interpretation |

| Hand over a collection of hard drives and reconcile what is where | F01, F05–F07, F10–F14, F21, F29. Begin with readable media or images and explicit scope; retain undecided versions. |
| A strong GUI is a minimum for a saleable desktop product | F14, F25, F27. Start prototype testing early; make independent usability a desktop release gate. Operator-delivered pilots may use the CLI internally. |
| Physical media awareness | F06–F08, F17, F29. Record assets, membership, locations and acquisition provenance, with uncertainty when identifiers conflict. |

| Filenames can be useful when contents cannot be recovered | F03, F09, F18, F21. Preserve metadata evidence and its source; do not imply names are always retrievable from an incomplete array. |
| Know what was lost instead of discovering it file by file years later | F02–F05, F20, F22. Maintain historical observations before failure, keep a searchable unresolved-file account and protect the catalogue independently. |

| Existing strengths in renamed trees, archives, comparisons and copy planning | F04, F10–F13, F16. Preserve useful code while correcting the boundary between heuristics, path-derived archive records and verified content. |

| Useful additions beyond the discussion | F15, F20–F32 add catalogue survival, safe previews, integrity review, supportability, preservation, capacity/failure domains, packaging and demand-led adapters. |

## Scope control

The first supported desktop release is a local catalogue and reconciliation product with explicit loss accounting. It needs the selected P0/P1 slices, a practical GUI, reliable handover and a tested preservation/support matrix. Full RAID recovery, every archive format, universal cloud integration, hosted multi-tenancy, AI classification and destructive cleanup are not prerequisites.

The priorities are planning decisions, not customer findings. Change them after pilot evidence, recording the affected feature IDs, acceptance tests, support burden and business reason. A feature moves to “implemented” only with a source revision and an observed validation result; a planning checkbox alone is insufficient.
